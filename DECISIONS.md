# Decisions

Running log. Newest decisions are appended at the bottom. Each entry: what we decided, why, and what it costs. Entries marked **[spec deviation]** change or tighten something in [`docs/SPEC.md`](docs/SPEC.md) and are worth a product review.

---

### D-001 · Name
The product is **Veradact**. The spec's working name "Deployment Ledger" survives only in `docs/SPEC.md`.

### D-002 · Phases run back to back **[spec deviation: process]**
The spec asks to stop for approval after each phase. The owner asked for the whole MVP in one pass without questions. Each phase still ends with tests, lint, typecheck and a commit; questions that would have been asked are recorded here as decisions so they can be revisited.

### D-003 · Stack details
Next.js **15** App Router (stable, well-understood APIs; 16 renamed middleware and changed caching defaults with little benefit for us). `postgres` (postgres.js) driver under Drizzle. Tailwind v4 for the vendor app only; the client page uses a small hand-written stylesheet so it stays plain and asset-free. Packages are consumed as TypeScript source, no build step.

### D-004 · AI candidates live outside the log; `item_created` replaces `item_proposed` + `item_accepted` **[spec deviation]**
The spec lists `item_proposed` and `item_accepted` as events. We keep AI candidates in a mutable `candidate` table (the review queue) and write a single `item_created` event when a human accepts or enters an item.
Why: the log is the dispute artifact, and the spec says nothing enters the ledger without a human accept. Putting machine guesses (most of which get rejected) into a tamper-evident record weakens it, and candidates contain quote text that must stay redactable. Provenance (`via: ai_candidate`, candidate id, model, prompt version, edited flag) is kept on the event, so the audit question "did a human change what the AI proposed?" is still answerable.

### D-005 · MCP server is its own app
`apps/mcp` is a plain Node `http` server using the MCP SDK's Streamable HTTP transport (stateless). The SDK transport expects Node request/response objects, and a separate process lets us rate limit and scale agent traffic independently of the vendor UI. It shares `core`, `db` and `export` with the web app.

### D-006 · Commands load state by folding the log
Each command folds the engagement's full event log to get current state, then appends. For pilot-sized engagements (hundreds to low thousands of events) this costs milliseconds and removes an entire class of drift bugs: the live path and the rebuild path run the same reducer from the same input. After each append the engagement's projection rows are deleted and rewritten from the folded state, so "rebuild equals live" holds by construction; the property test guards that property when this is later optimized. Snapshots ("log compaction") and a diffing writer can be added behind `loadState` / `writeProjections` without changing callers.

### D-007 · Hashes computed in TypeScript, linkage enforced in Postgres
Canonicalizing JSON in PL/pgSQL is error-prone, so hashes are computed in the app and re-verified by `verifyChain`. A `BEFORE INSERT` trigger still guarantees `seq` continuity and `prev_hash` linkage, and update/delete/truncate are blocked by both privileges and triggers. Timestamps are stored at millisecond precision (`timestamptz(3)`) so the hashed ISO strings round-trip exactly.

### D-008 · In-house canonical JSON
Sorted-key, whitespace-free JSON is ~30 lines. Not worth a dependency, and we control edge cases (reject `undefined`, non-finite numbers).

### D-009 · Item status with multiple contacts
For the current version, the latest response per contact counts. Any dispute → `disputed`; otherwise any confirmation → `confirmed`; otherwise `pending`. One confirmer is enough, and any confirmer can block. A per-engagement "all contacts must confirm" rule is a later setting.

### D-010 · Meaning of the "agreed" view **[spec clarification]**
The spec says agreed = "only items confirmed as of T, at the version that was confirmed", and also that a confirmation does not carry over to a revision. We read these together as: an item is in the agreed view at T only if its **current version at T** is confirmed. An item that was confirmed at v1 and revised to a pending v2 is *not* agreed; it is returned separately as `previouslyAgreed` for context, and spec export lists it under "Not confirmed — do not build" with a note that a revision is pending. This keeps coding agents from building a version the vendor has already moved away from.

### D-011 · Needs-review flags direct dependents only
Disputing, revising, superseding or withdrawing an upstream item flags its direct dependents. No transitive propagation ("keep this simple"); the flag is visible on the item and in the ledger filters.

### D-012 · Personal data off-log with keyed commitments
Client contact PII, the confirmer's identity/IP/user agent snapshot and dispute comments live in erasable side tables; source text, titles, filenames and participants live in `source_content`; free-text explanations live in `event_note` and the log carries enum reason codes. The log holds contact ids and HMAC commitments keyed per contact — erasure deletes the rows and keys, the commitments become unlinkable, and the hash chain is untouched. This combines the spec's two suggested options (separate tables + destroyable per-subject keys). Quotes need no commitment of their own: a span stores `source_id, source_sha256, start, end`, which binds the exact quoted text through the source's content hash.
Cost: item **statements** stay in the log because they are the vendor-authored agreement itself. Members are warned in the UI not to put personal data in statements. Dispute comments are erased along with the contact, which loses the client's stated reason for that dispute (the dispute event itself remains).

### D-013 · Unknown jurisdictions block unattested machine transcripts **[spec deviation: stricter]**
The spec blocks an unattested machine transcript only when a participant is known to be in an all-party-consent state. If jurisdictions are unknown, that rule silently allows the riskiest case. Default: unknown jurisdictions are treated like an all-party state (org setting `block_unknown_jurisdictions`, default on). The uploader can always proceed by attesting that all participants consented, which they should be able to do for any legitimately recorded call. Human-written notes, emails and chat exports are always allowed, as specified.

### D-014 · Extraction eval runs on recorded responses by default
The eval is a Vitest test. By default it replays recorded model responses so CI is deterministic and needs no API key; with `EVAL_LIVE=1` and `ANTHROPIC_API_KEY` set it calls the real model and prints precision and recall. The scoring, quote verification and matching code is the same in both modes.

### D-015 · Quote offsets are verified, and corrected when the quote is exact
LLMs copy text accurately but count characters badly. A candidate whose quote is an exact substring at the stated offsets is `exact`. If the quote is an exact substring elsewhere, we use the nearest occurrence and flag it `offset_corrected` (visible in the review queue). If it is not an exact substring anywhere, it is dropped and counted on the extraction run. Either way, nothing unsourced reaches a user.

### D-016 · Own magic-link auth instead of Auth.js
Login must resolve a user before a tenant is known, which with RLS means going through a narrow `SECURITY DEFINER` function, and every login must be audited. A small custom implementation (hashed single-use login tokens, hashed session tokens) is easier to make RLS-correct than adapting an auth library's adapter tables.

### D-017 · Rate limiting in Postgres
A fixed-window counter table works across multiple app instances without adding Redis. Load on public endpoints in pilots is tiny.

### D-018 · Link tokens are HMAC-signed and DB-revocable
`v1.<link_id>.<exp>.<sig>`: the signature binds the link to its contact and expiry; the database row provides revocation and open tracking. Rotating `LINK_SIGNING_SECRET` invalidates all outstanding links.

### D-019 · Authorization is per contact per engagement
A contact grants (or declines) authorization once per engagement, not once per request; the latest decision wins, so a contact who declined can return and grant. A new authorization text version requires a fresh grant.

### D-020 · Confirmation receipts anchor the chain externally (small addition)
A hash chain proves the log was not edited in place, but the vendor controls the database and could in principle rebuild a whole new chain. After a client submits responses, they receive a receipt email listing each item's short id, version and content hash plus the log head hash. The client then holds an independent copy that any rewritten history would contradict. Cost: one extra email per submission.

### D-021 · Business days
Monday to Friday in the engagement's IANA time zone; no holiday calendar in the MVP. Implemented with `date-fns` + `@date-fns/tz` because DST-correct zone arithmetic is not trivial.

### D-022 · Confirmation-rate denominator **[spec clarification]**
"Share of items sent for confirmation" is measured per **item version sent** (a revision sent again is a new attempt). Versions not yet 5 business days old are excluded (shown as "maturing"), and versions the vendor revised, withdrew or superseded before any client response inside the window are excluded as pulled rather than ignored. Without these exclusions the kill signal would fire on fresh pilots and on vendor churn.

### D-023 · Kind is immutable; short ids are allocated per kind
`ACME-R7` = the 7th requirement in engagement `ACME`. The id is allocated at command time and stored in the event payload, so it never changes and the projection stays pure. Changing an item's kind means superseding it with a new item.

### D-024 · Dependency rules
Dependents must be decisions or requirements (per spec). Upstream items can be any kind except the item itself; cycles are rejected.

### D-025 · Extraction runs synchronously after ingest
No job queue in the MVP: extraction runs in the ingest request after the source is committed, and its failure never rolls back the ingest. The `extraction_run` row records status so a retry button can re-run it.

### D-026 · Non-trivial dependencies we accepted
`mammoth` (.docx text), `jszip` (mammoth's zip reader, pinned as a direct dependency of `@veradact/ingest` for the decompression-bomb guard, D-060), `pdfkit` (record PDF), `fast-check` (property tests), `date-fns` + `@date-fns/tz` (zone-aware business days), `nodemailer` (SMTP), `zod` (payload and tool schemas; required by the MCP SDK anyway). Everything else small (canonical JSON, word diff, token signing, rate limiting) is written in-house.

### D-027 · AI-off engagements export without quotes
The spec says that with AI off "no source text is sent to any model provider". The spec export and the MCP server exist to feed coding agents, which are model providers. For AI-off engagements both omit quote text and cite the source by type, date and character offsets instead; statements (vendor-authored agreement text) are still included. The vendor app UI shows full quotes as usual.

### D-028 · Architecture review changes (Phase 0 critique)
An independent review before Phase 1 led to these changes, all reflected in `ARCHITECTURE.md`:
- Source titles/filenames and free-text reasons moved out of the log (`source_content`, `event_note`); the log carries enum reason codes.
- `engagement_head` maintained by the insert trigger; `verifyChain` reports `truncated` when the log is shorter than or diverges from a known head (tail deletion is otherwise undetectable).
- Every command takes an injectable clock, so seed and tests build weeks of history through the real append path.
- Hash round-trip rules: app-supplied ms timestamps only, `int8` parsed as number, integers only in payloads, `verifyChain` hashes raw stored values.
- Confirmation evidence snapshots the confirmer's name and email; links store the address they were sent to; exports verify evidence commitments.
- All tenant tables carry `org_id` (incl. request item/contact tables), composite `(id, org_id)` foreign keys, and a catalog sweep test for RLS coverage. Operational tables never reference projection tables.
- Spans on revisions are carried over unchanged or edited; zero spans means manual.
- Link open metric counts first interaction (POST), since mail scanners prefetch links; raw opens are shown separately.
- Client submissions are one transaction with an idempotent `submission_id`.
- Extraction never holds a transaction open across the model call; AI flags are re-checked before candidates are written.
- `.vtt`/`.srt` uploads are always machine transcripts for the consent gate.
- Client page is rendered by route handlers as plain escaped HTML (no React hydration), so a strict CSP needs no nonces.
- `decisionContext` cuts off by event seq, not timestamp; `as_of` dates mean end of day in the engagement time zone.
- Per-source HMAC quote commitments were dropped as redundant with `source_sha256` + offsets.

### D-029 · Contacts may change their response while the link is valid
The latest response per contact counts (D-009). Every response remains in the log, so a changed mind is visible in the record.

### D-030 · Orgs are created by an operator script
`pnpm org:create --name ... --slug ... --admin-email ...` runs with the admin database URL. Self-serve signup is not needed for 10–12 design partners. *Amended by D-062: self-serve sign-up exists behind `SIGNUP_ENABLED`; the script stays for operators.*

### D-031 · `record_candidates` is forced only where the model allows it
ARCHITECTURE §9.3 specifies a forced tool call. Claude Sonnet 5.5 (the default `ANTHROPIC_MODEL`), Opus 5.5, Fable 5.1 and Mythos 5.1 reject a forced `tool_choice` with HTTP 400. `AnthropicModelClient` therefore forces `record_candidates` on models that accept it and otherwise sends `tool_choice: auto` with `disable_parallel_tool_use`, a prompt instruction to call the tool exactly once, and `strict: true` on the tool so the input is schema-valid. A response without the tool call is retried once, then fails with `no_tool_call`. Server-side refusal fallbacks (a beta) are not enabled. A refusal fails the chunk with `refused`.

### D-032 · Database layer details (Phase 1a)
Choices made while implementing `packages/db`, within ARCHITECTURE §2 and §7:
- **Migration order.** `0000_extensions_and_roles` (hand-written: `citext`, guarded `veradact_app` creation) runs *before* the drizzle-kit-generated `0001_tables`, because table DDL uses `citext`. `0002_rls_and_grants`, `0003_append_only_log` and `0004_definer_functions` are hand-written; all five go through the Drizzle migrator in journal order. New tables need a `generate` migration plus a hand-written one adding RLS and grants (the catalog sweep and the cross-tenant table list fail until both exist).
- **`org` privileges.** The app role gets `SELECT, UPDATE` on `org` only; orgs are created by `pnpm org:create` (D-030) and never deleted by the app. All other operational and projection tables get `SELECT, INSERT, UPDATE, DELETE`; `event`/`audit_log` `SELECT, INSERT`; `engagement_head` `SELECT`.
- **No SQL timestamp defaults anywhere**, not only on `event.recorded_at/occurred_at`: every `created_at`, `expires_at` etc. comes from the application clock, so a forgotten clock fails loudly instead of mixing clocks in tests and metrics. Definer functions compare expiries with the database `now()`.
- **FK rule applied literally.** Projections reference only `engagement` (composite). Operational tables reference only org/app_user/engagement/client_contact/event, so `candidate.extraction_run_id`, `usage_event.api_token_id`, `confirmation_link.request_id` and other projection ids are plain uuids. No foreign key cascades. A catalog test enforces all of this.
- **Trigger errors.** Append-only rejections raise SQLSTATE `23001` (`event log is append-only` / `audit log is append-only`); chain violations raise `23000` with a message naming the failed check but no head values. The chain trigger is a `BEFORE INSERT` trigger and therefore runs before the RLS `WITH CHECK`; value-free messages keep a mis-targeted insert from learning another tenant's head.
- **Projection keys.** `contact_authorization` is keyed by `contact_id` (latest decision only, as the reducer keeps it); `item_response` by `(engagement_id, event_seq)`; `confirmation_request_item/contact` by `(request_id, item_id/contact_id)`; `item_dependency` by `(item_id, depends_on_item_id)`. `text_version` is text.
- **Shared test database.** The root Vitest globalSetup resets `veradact_test` once per run under an exclusive advisory lock and then holds a shared one until the run ends, so a second concurrent `pnpm test` waits instead of dropping the schema under the first.

### D-033 · Log Postgres errors through `getPgError`, never the thrown error
Drizzle 0.45 wraps driver errors in `DrizzleQueryError`, whose message is `Failed query: <sql> params: <values>` — the parameters can be names, emails, statements or tokens. CLAUDE.md and ARCHITECTURE §14 allow only SQLSTATE and constraint name in logs. `@veradact/db` exports `getPgError(error) → { code, constraint, message } | null`, which unwraps the cause; logging and error mapping must use it and must not log `error.message` of a query failure.

### D-034 · Supersede reason codes
§3 lists `reason_code` on `item_superseded` without values. Enum: `client_dispute | new_information | correction | scope_change | kind_change | duplicate | other`. `kind_change` covers D-023 (changing an item's kind means superseding it).

### D-035 · Payload value rules (hash round-trip safety)
Every payload value must survive a jsonb round trip byte-for-byte, so the zod schemas in `domain/events.ts` enforce: IDs are **lowercase** canonical UUID strings (any version; Postgres returns lowercase, and an uppercase id would hash differently from the stored row); digests are lowercase hex; timestamps inside payloads (`expires_at`) are exactly `Date.toISOString()` output; text has no NUL characters or lone UTF-16 surrogates (jsonb rejects both); numbers are safe integers. `canonicalJson` additionally rejects unsafe integers (> 2^53), Dates, Maps/Sets/typed arrays and other non-plain objects, symbol keys and cycles; keys sort by UTF-16 code unit. `parseEventDraft` drops `undefined`-valued keys (they would vanish in jsonb and break the hash) and rejects unknown keys (strict objects, so no PII can be added by accident). Also: statements are 1–2000 characters and not blank; an item or contact appears at most once per request; `authorization.text_version` is a string; the only `channel` is `email_link` (enum `ConfirmationChannelName`, named to leave `ConfirmationChannel` for the §15 seam). `parseEventDraft` also enforces who may author each type (`EVENT_ACTOR_TYPES`): client responses and authorizations by the contact named in the payload; `source_redacted`, `confirmation_revoked` and `contact_erased` by a user or `system`; everything else by a user — so `requested_by` and `ingested_by` are never null.

### D-036 · `occurred_at` rule and sealing
`source_ingested`, `item_created` and `item_revised` take `occurred_at` from the draft (falling back to `recorded_at`); every other event has `occurred_at = recorded_at`, whatever the draft says (`OCCURRED_AT_EVENT_TYPES`, `resolveOccurredAt`). The pure core of the append path is `nextRecordedAt(clock(), head.recordedAt)` + `sealEvent(draft, { orgId, engagementId, seq, prevHash, recordedAt })`; the DB append API should call exactly these so the app-computed hash and the trigger-assigned `seq`/`prev_hash` agree.

### D-037 · Reducer details
- Needs-review (D-011) flags only **active** direct dependents; a superseded or withdrawn dependent is never flagged. Reasons accumulate (`{upstreamItemId, cause, seq}`) until the dependent is revised or `review_cleared`.
- Any event whose payload names an existing item updates that item's `updatedAt`/`lastSeq`; so does a needs-review flag raised on a dependent. `createdAt` is the `recorded_at` of `item_created`.
- Total for well-formed events: references to unknown items/sources/requests are ignored; a duplicate `item_created`/`source_ingested`/`confirmation_requested` id is ignored (first write wins); repeated revocations and redactions keep the first time.
- State shape refinements of §5.1: `engagement` is null before genesis; `dependsOn` is `Map<upstreamId, addedSeq>` (the projection needs `added_seq`); request revocations are `revokedContacts: Map<contactId, at>` + `revokedAllAt` (the projection needs `revoked_at`); each item caches its derived `status`; responses and versions keep their seq.

### D-038 · Projection row conventions
`projectRows(state)` returns exactly the §2.3 columns (camelCase keys, Dates for timestamps). jsonb columns use snake_case keys like payloads: `review_reasons = [{upstream_item_id, cause, seq}]`, `spans = [{source_id, source_sha256, start, end, carried}]` where `carried` means the identical span was on the previous version. `item_response` has no `channel`/`evidence_commitment` columns in §2.3, so they are not projected (they stay in the log and in `EngagementState`). `source.ingested_by` is the event's actor, falling back to `attestation.attested_by`. `confirmation_request_item` has one row per (request, item), matching its primary key. Rows are sorted by `PROJECTION_SORT_KEYS` (the tables' primary keys, `item_response` by `event_seq`); a DB dump compared with them must use the same `ORDER BY`.

### D-039 · `verifyChain` semantics
Rows must be the full log from seq 1 in stored order; a gap, duplicate or reordering is `seq_gap`. Per row the checks are seq, then `prev_hash`, then the recomputed hash (an unhashable row is `hash_mismatch`, never a throw). `firstBadSeq` is the expected seq at the failing position; `checked`/`headSeq`/`headHash` describe the last good row (0 and 64 zeros for an empty log). `expectedHead` is checked after the chain: shorter log → `truncated` at `headSeq + 1`; different hash at `expectedHead.seq` → `truncated` at that seq. `expectedHead.seq = 0` is ignored.

### D-040 · Replay details
- Agreed view (D-010): an item's `confirmations` are the latest response per contact on that exact version (all confirmations, since the status is confirmed). Only **active** items appear in `items`, `previouslyAgreed` or `notConfirmed`; superseded and withdrawn items appear in none. `previouslyAgreed` uses the latest earlier version whose own responses make it confirmed. `notConfirmed` lists every other active item with `revisionPending` set for previously agreed ones (the "do not build" list).
- `diff(T1, T2)`: `added` = items created in (T1, T2] (shown at their T2 state, not also in `revised`); `revised` = items that existed at T1 with a different current version at T2; `confirmed`/`disputed`/`superseded`/`withdrawn` come from events in (T1, T2]; `changes` = every item whose version, hash, status, lifecycle or needs-review differs. `T1 > T2` throws.
- `decisionContext` defaults to the item's latest version and returns null for an unknown item or version.

### D-041 · Jurisdiction codes for the consent gate
Matching is case-insensitive and ignores surrounding whitespace. Accepted: two-letter codes (`CA`), `US-XX` (also `US_XX`, `US XX`) and full US state names (`California`, `District of Columbia`). A two-letter code that is a US state code is read as that state, so `DE` is Delaware, not Germany — the conservative reading, since only US states are on the all-party list and attesting consent always lets the uploader proceed. Anything else (a typo, `Germany`, `DE-BY`) is **unrecognized and treated as an unknown jurisdiction**, which blocks an unattested machine transcript under D-013. The stored attestation records the normalized, sorted codes and the normalized policy list; `CONSENT_POLICY_VERSION = 1`.

### D-042 · Business-day edge cases
`addBusinessDays(t, n, tz)` steps over local calendar dates in `tz` and keeps t's local wall time. A start on Saturday or Sunday counts the following Monday as business day 1 (Saturday + 1 = Monday, same time). A wall time that does not exist on the target day (spring-forward gap on a weekday, e.g. Africa/Cairo) resolves forward by the gap; an ambiguous one resolves as `TZDate` does (standard-time occurrence). `businessDaysBetween(a, b, tz)` counts weekdays d with date(a) < d ≤ date(b) and is the inverse of `addBusinessDays`.

### D-043 · Metric interpretation details
Metrics are computed as of `now` (later events, link timestamps and usage rows are ignored, like replay). A version is "pulled" when the first revise/withdraw/supersede after it was sent is recorded before `window_end` and no response to that version precedes it (compared by seq). A confirmation exactly at `window_end` counts. The median time to confirm includes confirmations on still-maturing versions. Link figures count only links whose email was sent. Churn counts a revision when any earlier `item_confirmed` exists on the item. CSV cells whose text starts with `= + - @`, tab or CR are prefixed with `'` so spreadsheets do not evaluate them.

### D-044 · Export rendering details
AI-off exports hide source titles as well as quotes (`quoteFor` is never called) and say so once in the header. User text is markdown-escaped and statement newlines are collapsed so a statement cannot inject headings or HTML. The spec's "Log head" is the head of the log the view reflects; a separate "Current log head" line appears when they differ. A revised item's previously agreed version never appears in the spec (it is listed under "Previously agreed versions" in the record). Dates render in the engagement time zone with an explicit UTC offset; record tables use exact UTC ISO timestamps. PDFs are deterministic (metadata dates come from `generatedAt`) and use built-in Helvetica only; characters it cannot draw become "?" while the markdown keeps the exact text.

### D-045 · Vendor auth and session details (web shell)
Choices made implementing ARCHITECTURE §2.1/§14 in `core/auth`, `core/org`, `core/api-tokens` and `apps/web`:
- **Lifetimes and limits.** Login token 15 min, session 30 days (cookie `vd_session`: `HttpOnly`, `SameSite=Lax`, `Secure` when the request or `APP_URL` is https, `Path=/`). `last_seen_at` is written at most every 5 min and `api_token.last_used_at` at most every 60 s (conditional `UPDATE`, so idle requests write nothing). Magic-link requests: 20 per 15 min per IP, 5 per 15 min per email; verification: 30 per 15 min per IP.
- **No enumeration.** Known and unknown addresses take the same path up to the response (both limits charged, a token generated, the definer lookup run) and return the same result; the web app delivers the email in `after()` so SMTP latency cannot reveal account existence. The login page shows "check your email" even when rate limited.
- **The magic link is consumed on POST, not GET.** `GET /auth/verify?token=…` only renders a minimal "Sign in to Veradact" page (plain HTML, no JavaScript, `Referrer-Policy: no-referrer`, `X-Robots-Tag: noindex, nofollow`, `Cache-Control: no-store`, strict CSP) whose button POSTs the token; the POST consumes it and sets the cookie. Corporate mail scanners that prefetch links therefore cannot burn it. The POST rejects a form whose `Origin` is not the app's (login CSRF), and every failure redirects to the same `/login?error=link`.
- **Deactivation** sets `deactivated_at`, replaces email with `deleted+<user id>@invalid` and name with "Deactivated user" (§6), revokes all sessions and API tokens, and frees the address for a new invite. An admin cannot deactivate themselves, so every org keeps an admin.
- **Who sees what.** Members can read org settings and the user list; only admins change settings, invite or deactivate. API tokens: members list and revoke their own; admins see and revoke every token in the org. Other users' tokens look like missing ones (`not_found`).
- **Settings ranges.** `retention_days` null or 1–3650; `reminder_business_days` 1–10; `all_party_states` two-letter US state/DC codes only (stored upper-cased, de-duplicated, sorted).
- **Audit metadata.** `ai.toggle` → `{scope: "org", before, after}`; `settings.update` → `<field>_before/_after` for each changed scalar and `all_party_states_count_before/_after`; `user.deactivate` → revoked session/token counts. API token display prefix is `vdt_` + 8 characters.
- **Rate-limit keys** are plain `sha256(scope:window:id)` as specified, so an email or IP can be confirmed by guessing; rows only live for one window (prune with `pruneRateLimitBuckets`). Keying with an HMAC secret is a cheap hardening if that matters later.

### D-046 · Logging and dev environment plumbing
- `core/log.ts` enforces the logging rule in the type system: field values may be numbers, booleans, null, string-literal (enum) types or ids wrapped in `logId()`; a plain `string`, object or Date does not compile. At runtime, strings that do not look like an id or enum token become `"[redacted]"`. `writeAudit` applies the same type to `metadata` and throws on unsafe values. Logs are silent under Vitest unless `LOG_LEVEL` is set.
- `apps/web/next.config.ts` loads the repo-root `.env` at module load (not inside a phase function) when `NODE_ENV` is not production: Next only forwards env changes made while the config module loads to its dev worker and drops later ones on its env reloads. The dev request log ignores `/auth/verify` and `/c/` so tokens never reach the terminal.
- Playwright's global setup clears `rate_limit_bucket` in the dev database (admin URL, test setup only), because every local run comes from the same IP and would otherwise trip the per-IP login limit after a few runs.

### D-047 · Store and command details (Phase 1c)
Choices made implementing ARCHITECTURE §5.2–§5.3, §6 and §8.4 in `core/store`, `core/commands` and `core/queries`:
- **Validate under the lock.** Commands call `lockAndLoad` (the §5.2 advisory lock, then the fold) *before* validating, so checks such as "submission id unused", short-id allocation and version matches cannot race. `appendEvents` re-takes the (re-entrant) lock and accepts the caller's folded `state`, which it uses only if `engagement_head` still matches its head (one select instead of a second fold). `appendEvents` also enforces the log's structural rule: `engagement_created` is the genesis event for that engagement and appears only at seq 1. All drafts of one call are inserted in one multi-row statement (the chain trigger checks them row by row).
- **One clock read per command.** Commands read `clock()` once and append with a fixed clock, so all events of a command share a millisecond (as a client submission must); operational timestamps derived from the append (`confirmation_link.created_at`, link `revoked_at`, `client_contact.erased_at`, `source.redacted_at`) use the event's `recorded_at`. `appendEvents` itself still calls the clock exactly once per draft.
- **Errors.** Ledger rule violations throw `DomainError` (extends `CoreError`) with a stable `code` from `LEDGER_ERROR_MESSAGES`, one fixed message per code and `details` limited to ids, enums, counts and validation paths; `ConsentBlockedError` adds `rule`, `blockingStates` and the user-facing `explanation`. A zod rejection inside `appendEvents` becomes `invalid_event` with the issue paths.
- **Span input.** `{ sourceId, quote }` resolves to the quote's unique occurrence (overlapping occurrences count; 0 → `quote_not_found`, >1 → `quote_ambiguous`); `{ sourceId, start, end, quote? }` is range-checked and, with a quote, must match exactly (`quote_mismatch`). Quotes are NFC/newline-normalized like source text. A version citing several sources takes `occurred_at` from its first span's source. Revisions take `removeSpans` (must match current spans) and `addSpans`; everything else is carried unchanged, and zero remaining spans makes the version `manual: { entered_by: <reviser> }`.
- **Ingest rejects non-normalized text** (`source_not_normalized`) instead of normalizing it, because the caller's segment offsets would no longer line up; callers pass `parseSource` output.
- **Evidence snapshots for authorizations too.** `confirmation_evidence` gets a row for every event that carries an `evidence_commitment` — authorization events as well as responses — so record exports can verify all of them.
- **Stricter client checks.** `recordAuthorization` rejects revoked and expired requests (like responses). In `recordClientResponses` the duplicate-submission check comes first, so resubmitting an already recorded form is a no-op (`duplicate: true`) even after the link was revoked or expired. `requestConfirmation` de-duplicates item and contact ids and fails with `version_mismatch` when the member's version/hash is no longer current.
- **Archive/reactivate** change the engagement row only and are audited as `engagement.update` with `{status}`. `redactSource`, `revokeConfirmation` and `eraseContact` accept `userId: null` for the `system` actor (retention and other jobs).
- **Not here:** dispute/decline notifications, link email delivery, the authorization-text version check (D-019) and extraction candidate status updates belong to the confirmation and extraction flows, which call these commands (with their own `tx` when they must write in the same transaction).

### D-048 · MCP server and shared export loaders
Choices made implementing ARCHITECTURE §10–§11 in `@veradact/export/server` and `apps/mcp`:
- **Export depends on core and db at runtime, through a subpath only.** The DB-aware loaders (`resolveEngagementRef`, `resolveItemRef`, `loadExportContext`, `loadSpec`, `loadRecord`, `recordUsage`, `parseAsOf`) live in `@veradact/export/server` so the web app and the MCP server build exports the same way; the root entry point stays pure rendering. Core never imports export.
- **Ref resolution.** Engagement refs are a UUID or a short code, item refs a UUID or a short id, all case-insensitive; anything else, unknown or another tenant's resolves to null (RLS), and the MCP tools answer the same "Not found" for all of them. Short ids are unique per org because short codes are.
- **`as_of` input.** `YYYY-MM-DD` = 23:59:59.999 of that day in the engagement time zone (`TZDate`, DST-correct); timestamps must carry `Z` or an offset. A zone-less timestamp is rejected rather than guessed (server zone vs engagement zone), with a message that tells the agent the accepted formats.
- **Evidence status in the record.** An erased contact is `erased` before anything else is checked; otherwise a missing snapshot or HMAC key is `missing`, and the commitment is recomputed with core's `evidenceCommitment` over the snapshot (name, email, ip, user agent) and compared in constant time (`verified` / `mismatch`). Dispute comments are included (null once the contact is erased).
- **Stateless transport, one McpServer per request.** Each POST gets a fresh `McpServer` bound to the token's org/user and a `StreamableHTTPServerTransport` with `sessionIdGenerator: undefined` and JSON responses; GET/DELETE answer 405. Bodies over 1 MB are refused by the transport (`maxRequestBodySize`, 413).
- **Rate-limit order.** The per-IP limit (120/min) is charged *before* the token is resolved, so floods of well-formed bogus tokens cannot reach the definer lookup unthrottled; the per-token limit (60/min) is charged after authentication. The client IP follows the web app's rule (first `X-Forwarded-For` entry), so the server must run behind a proxy that overwrites it.
- **Metering.** `usage_event(kind='mcp_fetch')` is written in the tool's tenant transaction, only for successful calls; not-found and invalid-input calls roll back with it and are only logged (ids and an outcome enum).
- **What MCP output leaves out.** `get_item` never exposes dispute comments (client-authored, erasable text) and, for AI-off engagements, neither quotes nor source titles (D-027, D-044). Unconfirmed, superseded and withdrawn items carry `do_not_build: true` with a warning; a confirmed item that needs review keeps `do_not_build: false` with a warning to check with the team.

### D-049 · Client confirmation flow details (Phase 3)
Choices made implementing ARCHITECTURE §8 in `core/confirmation`, `core/notifications`, `core/jobs` and the `/c/[token]` route handlers:
- **Authorization text `auth.v1`** (`confirmation/authorization-text.ts`) names the vendor org, the client company and the engagement only (it is stored in the event, §6): what is processed and stored, erasure on request, no training, and what declining means. Names are collapsed to one line so they cannot reshape the text. The authorization form carries `sha256` of the text it showed; if the rendered text differs at POST time (a name changed in between) nothing is recorded and the new text is shown, so the stored text is always the one the contact saw. A grant under any other text version counts as "authorization required" for the client page and for submissions (D-019).
- **Link validation uses the projections, not a fold**: `link_resolve` → constant-time HMAC check (one HMAC is computed against a dummy contact id for unknown links, so that path costs the same) → token `exp` and `expires_at` → link not revoked → `confirmation_request_contact.revoked_at` null, request not expired, contact not erased and PII present. Every failure is the same `{ ok: false }` → one 410 page.
- **Post/redirect/get for authorization** (303 to `/c/<token>?step=…`), so a reload never writes a second authorization event. GETs carrying `?step=` are not counted as opens; only a fresh visit increments `open_count`. The receipt is rendered directly in the submit response: a reload resubmits the same `submission_id`, which is a no-op that shows the same receipt and says nothing new was recorded.
- **Unchanged responses are dropped.** The items form preselects the contact's existing response (D-029). On submit, skips and answers equal to the existing response (same decision, and for disputes the same comment) are not written, so resubmitting the defaults does not add events; if nothing remains the page says so. A form that answers an item revised since it was rendered, or whose hidden `version:content_hash` binding is missing or different, is "stale": nothing is recorded and the page is shown again (409).
- **Notifications go to the requester only** (the member who sent the request), in the same transaction as the client's events: one row per disputed item, one per decline. The emails to the requester name the contact and the item short ids but carry no comment or statement; the contact's receipt is the only email with item content.
- **Delivery after commit.** `sendConfirmationRequest` commits the request, then delivers per link; a failed delivery keeps the request and leaves `email_sent_at` null (reported to the member, who can revoke and resend). Client emails (receipt, notices) are sent after the transaction and never fail the action.
- **Reminders claim before sending.** A link is claimed with a conditional `UPDATE … SET reminder_sent_at … WHERE reminder_sent_at IS NULL AND <still eligible> RETURNING`, committed, then emailed; a failed delivery releases the claim for the next run. Two concurrent runs cannot both send; a crash between claim and send loses that reminder (never two). Eligibility is evaluated from the projections; a dispute counts as a response. `runReminders` takes `onlyOrgIds` because test files share one database. The reminder URL re-signs the same link (tokens are deterministic and never stored).
- **Client-page rate limits:** 300 requests per 15 minutes per IP, 120 per link (keyed by the link id parsed from the token, unverified), on GET and POST.
- **CSP adds `img-src 'self'`** to ARCHITECTURE §8.3's policy (per the Phase 3 brief); the pages load no images. Next config headers override route-handler headers, so `next.config.ts` sets `Referrer-Policy: no-referrer` for `/c/:path*` as a later rule; vendor pages keep `strict-origin-when-cross-origin`.
- **Seeding the metrics scenario** (`seedMetricsScenario`) replays `buildMetricsScenario`'s log through the real commands with a clock set to each event's `recorded_at` (fresh ids, real content hashes, the real authorization text), then copies its link timestamps and usage rows. The chain verifies and rebuild equals live, and the computed metrics equal the scenario's expected numbers.

### D-050 · Extraction run and review queue details (Phase 2)
Choices made implementing ARCHITECTURE §9.3–§9.4 in `core/extraction` and `core/review`:
- **Where AI-off is enforced.** `runExtraction` is the only code path that sends source text to a model (`ModelClient.extract`). Its first transaction reads `org.ai_enabled` and `engagement.ai_enabled` before it reads the source text, and throws `AiDisabledError` (`code: ai_disabled`, `scope: org | engagement`) before `modelClientFactory` is called, so no client is constructed and nothing is written. The second transaction re-reads both flags `FOR SHARE` (a concurrent toggle waits for it); if either is off the results are thrown away and the run ends `status = 'discarded'`, `error_code = 'ai_disabled'`. The schema's run statuses are `running | succeeded | failed | discarded`, so the brief's `discarded_ai_off` is that status plus that code rather than a new enum value.
- **The model client is built inside transaction 1, after the check**, because `extraction_run.model` (= `client.name`) is NOT NULL. A factory that throws gives a `failed` run with `error_code = 'client_unavailable'`. Model errors are mapped from `ModelClientError.code` / `IngestError.code` (else `unknown`; Postgres errors `db_error`). Failed and discarded runs return a result instead of throwing, so the ingest that came before is never affected (D-025).
- **Candidate hygiene.** Quotes are verified against the stored text re-read in transaction 2 (a source redacted during the model call fails the run with `source_redacted`). Statements over 2,000 characters are dropped and counted. `suggested_depends_on` keeps only `#n` and short-id-shaped references (at most 20). `revises` must name an existing, active item of the same kind; otherwise the link is dropped, the candidate stays as a new item and the run result carries a note (`revises_not_found | revises_not_active | revises_kind_mismatch`). Notes are returned to the caller, not stored (the candidate table has no column for them).
- **Re-running extraction replaces the source's pending candidates** from earlier runs (deleted when the new run succeeds). Accepted and rejected rows stay, so the review history is kept and the queue never shows duplicates.
- **Accept.** `acceptCandidate` locks the candidate row, folds the log under the engagement lock and runs `createItem`/`reviseItem` with the caller's transaction, then marks the row `accepted` with `resulting_item_id` — one transaction. Revisions replace every span of the current version with the candidate's verified span, use reason code `new_information`, and keep the item's kind (a kind edit on a revision is rejected: `revision_kind_immutable`; changing kind means superseding, D-023). If the revision target was superseded or withdrawn meanwhile, the candidate becomes a new item with a note. Dependency references (`#n` → the item an accepted same-run candidate produced; short ids; item ids) that do not resolve, point at inactive items, would create a cycle, or hang off a kind that cannot have dependencies are dropped and returned as notes; the web app shows them after the accept. `provenance.edited` is true when the statement, the kind or the dependency list differs from the suggestion.
- **Who may toggle engagement AI.** Any member of the org (like the other engagement settings); the org switch stays admin-only. Both write `ai.toggle` with `{scope, before, after}`; a no-op toggle writes nothing.

### D-054 · Replay and export screens (Phase 4b)
- **Replay is GET-only.** Every view is a URL (`as_of`, `view=known|agreed|compare`, `kind`, `status`, `from`, `to`, `decision`, `version`). ### D-055 · Retention job, and redaction deletes every candidate (Phase 5)
- **`runRetention({ db, now })`** (`core/jobs/retention.ts`) iterates `jobs_list_org_ids()`; for an org with `retention_days` it lists unredacted sources with `recorded_at < now − retention_days` and calls the real `redactSource` with `userId: null` (system actor) and `reason_code: 'retention'`, one transaction per source so one failure does not hold back the rest (failures are logged by id and retried on the next run; a source a member redacted meanwhile is skipped). Days are 24-hour periods from `now`, not calendar days in a time zone. The source date (`occurred_at`) is irrelevant: the window measures how long the text has been held. `runScheduledJobs` runs reminders, then retention; `POST /api/cron/retention` runs retention alone (same bearer check as reminders, now shared in `apps/web/src/lib/cron.ts`).
- **Rate-limit pruning lives in the retention run** (windows older than 24 h, `RATE_LIMIT_BUCKET_MAX_AGE_MS`, comfortably above the longest window, 15 min). `pruneRateLimits: false` exists only because test files share one database: a prune with a fake `now` would delete other tests' live windows.
- **`redactSource` now deletes all candidates of the source**, not only pending ones (ARCHITECTURE §6 updated). Accepted and rejected rows copy the source text (`quote`, `speaker_label`, model-written `statement`), so keeping them broke the promise that redaction removes the text. Item provenance keeps the candidate id; the item detail query already tolerates a missing candidate row (it then shows no verification flag). Retention therefore needs no candidate step of its own. `event_note` rows are not touched: they belong to member actions (revise, withdraw, supersede, redact), not to the source.
- `runExtraction` holds the source text `FOR SHARE` in tx 2 (see D-058), so a redaction racing an extraction cannot leave candidates behind.

### D-056 · Security hardening (Phase 5 review)
- **Client IP behind proxies.** Both apps take the `X-Forwarded-For` entry appended by the first trusted proxy, counted from the right (`TRUSTED_PROXY_HOPS`, default 1, `core/security/client-ip.ts`); the old rule (leftmost entry, then `X-Real-IP`) let any client choose its rate-limit key and its recorded evidence IP. Default 1 because Next fills the header with the socket address when it is absent, so local dev and a single load balancer both work unconfigured; `0` ignores the header (web: "unknown", MCP: socket address). Invalid values throw at startup.
- **CSRF.** `isCrossSite` (`apps/web/src/lib/request.ts`) is shared by `/auth/verify` and the client POST: `Sec-Fetch-Site` decides when present; without it a foreign Origin is refused, and `Origin: null` is refused on `/auth/verify` (login CSRF from sandboxed frames or pre-2023 browsers) but allowed on `/c/*`, where the no-referrer policy makes old browsers send `null` on the page's own forms and the token itself is the credential. A request with neither header (curl, a script) is allowed: it already holds the token.
- **Body caps before parsing.** `/auth/verify` 4 KB, `/c/*` 256 KB (Content-Length and bytes actually read, `readFormData`). 256 KB rather than the suggested 64 KB: one maximum-length dispute comment (5,000 characters) can take 45 KB once non-ASCII text is percent-encoded, and a form may carry several.
- **Session cookie `Secure`** follows `APP_URL`'s scheme, not `X-Forwarded-Proto` (a header a client can send when the app is reached directly). **HSTS** (`max-age=31536000; includeSubDomains`) is in every production build's headers: Next evaluates `headers()` at build time, where `APP_URL` may be unset, and browsers ignore HSTS on plain-http responses; dev never sends it because it would pin `localhost` to https. No nonce CSP for the vendor app: Next's inline bootstrap scripts need per-request nonces, which forces dynamic rendering everywhere — not worth it for the MVP.
- **Secrets.** `assertProductionSecrets` (`core/security/secrets.ts`) runs from Next's `instrumentation.ts` (Node runtime only, via `instrumentation-node.ts` so the edge bundle never imports core) and from `pnpm jobs:run`: in production `LINK_SIGNING_SECRET` must be set, and any of `SESSION_SECRET`, `LINK_SIGNING_SECRET`, `CRON_SECRET` that is set must be ≥ 32 characters and not start with `dev-only` or contain `change-me`. `linkSigningSecret()` and the cron routes repeat the check at use. `SESSION_SECRET` is not read by any code today (session and API tokens are 256-bit random values stored as SHA-256); it stays reserved and checked so a deployment copied from `.env.example` cannot ship the placeholder.
- **`.docx` decompression bombs.** Before mammoth runs, `assertZipWithinLimits` (`packages/ingest/src/zip-guard.ts`) walks the central directory, caps entries (2,000) and inflates every entry with zlib's `maxOutputLength` against a shared 25 MB budget — the real inflated size, since declared sizes can lie — then the extracted text must fit the 5 MB source limit. ZIP64, encryption and methods other than store/deflate are refused. No worker thread: the pre-inflation bounds what mammoth sees, and a worker would need a separate entry file that Next's server bundling and the TypeScript-source packages make brittle. (The hand-written reader was replaced by JSZip itself, D-060.)
- **Enumeration and timing.** `requestMagicLink` now does the user lookup, the token insert and the email in one deferred task, so known and unknown addresses return after the same work. Inviting an address that already belongs to a user (in any org) gets one generic message; the conflict is logged by SQLSTATE for operators.
- **Dependencies.** `pdfkit` and `mammoth` are direct dependencies of `apps/web` so `serverExternalPackages` can resolve them at runtime (otherwise Next bundled pdfkit with absolute paths to its font files).

### D-057 · Erasure is admin only; client email domains; AI-off outputs carry no contact names
- **`eraseContact` is admin only.** It irreversibly deletes confirmation evidence, so it joins the other admin-only actions. The role is read from `app_user` inside the command's transaction rather than taken from the caller, so no entry point can skip it; `userId: null` (system jobs) is still allowed. Members see the button disabled with the reason.
- **Self-confirmation guard.** A member could add a "client contact" with an address they control and confirm items themselves. An engagement may list the client's email domains (`engagement.client_email_domains`, row only like the AI switch, changes audited as `engagement.update` with counts). Adding a contact — or changing a contact's address — outside those domains (subdomains included) needs an explicit acknowledgement and writes `contact.outside_domains` (ids and a count only). The item page shows the confirmer's email domain from the evidence snapshot taken at response time (null once erased); the record export shows it next to each responder and authorizer as well. Empty list = no check, so nothing changes for existing engagements.
- **AI-off engagements** also keep contact names out of what goes to coding agents: MCP `get_item` says "client contact" for each response, and the spec export (file download and MCP `get_confirmed_spec`) says "Confirmed by: Client contact (date)". The record export, a vendor-internal dispute artifact, keeps names.

### D-058 · Correctness fixes from the Phase 5 review
- **Submissions are bound to their contact and request.** A `submission_id` counts as a duplicate only when the recorded responses have the same `contact_id` and `request_id`; otherwise `recordClientResponses` throws `submission_mismatch` and the client page shows the stale page — never another contact's receipt. The owner is found from the folded item responses, so the state shape and reducer are unchanged.
- **D-019 in every channel.** `recordClientResponses` itself requires the contact's latest authorization to be a grant of the current `AUTHORIZATION_TEXT_VERSION` (previously only the email-link channel checked the version).
- **Content hashes are recomputed on append.** `appendEvents` rejects an `item_created` / `item_revised` whose `content_hash` is not `itemContentHash` of the version (kind from the item for revisions) with `invalid_event`, so no caller can bind confirmations to a hash that does not describe the content.
- **Consent: "US" is not a state.** `US`, `USA`, `United States` and `US-XX` with a non-state `XX` are unrecognized jurisdictions (→ unknown → blocked when unattested, D-013); before, `US` was read as a known non-all-party jurisdiction.
- **Extraction.** tx 2 reads `source_content` `FOR SHARE` (redaction deletes that row first, so it waits and then deletes the new candidates, or it finished first and the run fails with `source_redacted`). The AI flags are read once more right before `client.extract`; the remaining window (text already sent when a switch flips mid-call) is documented in ARCHITECTURE §9.3.
- **Client page races never 500.** `clientSubmit` maps every rule violation (revoked or expired request, erased contact, items revised, tampered form) to the stale page and comment problems (including NUL characters) to field errors; the route re-resolves the link after a stale result, so a link that died meanwhile gets the 410 page.

### D-059 · Phase 5 test layout
- **Timeouts.** `packages/core` and `packages/db` got Vitest configs with 30 s test and hook timeouts (their `*.int.test.ts` share one database with every other project under a full parallel run; the 5 s default flaked). Playwright's `expect` timeout is 10 s because the dev server compiles each route on first use, and the settings save waits up to 20 s. A hang still fails. The remaining e2e flakes were not timeouts: a route compiled for the first time mid-run (`/logout`, `/`) made Fast Refresh reload *another* test's open page, which swallowed its click or form post. Playwright's global setup therefore signs in once and renders every screen and route handler before the tests start (the web server is up by then), so a cold `pnpm test:e2e` behaves like a warm one; it adds about 15 s on a cold server and under a second on a warm one.
- **Cross-tenant tests at the application layer.** `core/src/security/cross-tenant.int.test.ts` is table-driven: for every command and query that takes an id, org B's id must give the same outcome as a random UUID, which must be a not-found code or an empty/null result (secondary references such as a dependency target must match the unknown-id error); afterwards every row of every tenant table of org B is compared with a snapshot. The `@veradact/export/server` loaders are covered the same way in `apps/mcp/src/export-loaders-cross-tenant.int.test.ts`, because core cannot import export and the export package belongs to its own phase.
- **Audit coverage.** `core/src/audit-coverage.int.test.ts` writes every core action through the functions the web app calls and scans all metadata values (ids, enums, counts, booleans) and all serialized rows for the names, emails, statements, notes and tokens involved. The export actions are written by `apps/web/src/lib/export-download.ts` (tested there); the coverage file also checks statically that every `AUDIT_ACTIONS` member appears in some non-test source file, so a new action cannot be added without a writer.

### D-060 · Review fixes after Phase 5
- **The .docx guard reads archives with JSZip itself.** The hand-written central-directory walk disagreed with JSZip 3.10 (mammoth's zip reader) in ways an attacker controls: JSZip keeps reading central records past the end record's declared count, and when the directory does not end at the end record it shifts every offset by the difference (data "prepended" to the archive). Both let a harmless entry pass the guard while mammoth inflated a hidden bomb. `assertZipWithinLimits` now (1) refuses any archive whose central directory is not exactly the declared records filling `[offset, offset + size)` right before the end record (also ZIP64 and multi-disk) — real .docx files always are, and it caps the record count before JSZip allocates per record; (2) loads the archive with `JSZip.loadAsync` (parses, inflates nothing) and inflates every non-directory entry JSZip sees through `internalStream("uint8array")`, counting chunks against the shared 25 MB budget and pausing the stream at the first byte over it, so memory stays at the stream's chunk size rather than the entry's. `jszip` is a direct dependency pinned to the version mammoth resolves (3.10.2); a test fails if the two ever resolve to different packages. Step 2 alone also rejects both bypass shapes (tested), so step 1 is defence in depth, not the only check. The guard is async now.
- **`clientAuthorize` never 500s after a race.** Domain errors from loading the link's names (`contact_erased`, `request_not_found`) or from `recordAuthorization` (`request_revoked`, `request_expired`, …) answer `{ status: "stale" }` like `clientSubmit`; the `/c/[token]` handler re-resolves the link and shows the 410 page when it died, else the page again with a notice.
- **`appendEvents` refuses `item_revised` for an unknown item** with `item_not_found`; before, the content-hash check was skipped when the item's kind could not be looked up.
- **Replay "future date" notice** compares calendar days in the engagement time zone (`isAfterLocalToday`), so "as of today" (the end of today, after `now`) is not called the future.
- **`TRUSTED_PROXY_HOPS=0` is refused for the web app in production** (`webTrustedProxyHops`, run from `instrumentation-node.ts`): Next exposes the client address only through `X-Forwarded-For`, so with 0 every request keyed its per-IP limits on "unknown" and one client could exhaust them for all. Running without a proxy is unsupported in production; the value must equal the number of trusted proxies. Development and the MCP server (which falls back to the socket address) still accept 0.
- **Invitations are rate limited** to 20 attempts per hour per org (`INVITE_RATE_LIMIT`, scope `user_invite_org`, checked after the admin and input checks, before the insert, so conflicts count). **Residual risk, accepted:** emails are unique across orgs (one org per user in the MVP), so an admin who invites an address that already belongs to another org's user still gets the generic conflict message instead of a new user — and can infer that the address is registered somewhere. The rate limit bounds how fast that can be probed (20 addresses per hour per org, and an org is created by an operator, D-030 — no longer true with sign-up on, see D-062); removing the signal entirely needs multi-org membership or invitations that only take effect when the invitee accepts, both out of MVP scope.

### D-061 · Supabase as the Postgres host **[spec deviation: stack]**
The owner asked to use Supabase. The spec says "Postgres 16 with Drizzle; docker-compose for local dev".
- **Supabase hosts Postgres and nothing else.** Local development runs the Supabase CLI stack (`supabase/config.toml`: Postgres 17, Mailpit, Studio and the Data API on the same ports as before; auth, storage, realtime, edge functions and analytics are off) instead of docker compose. `pnpm db:up` = `supabase start` plus `bootstrap-local.ts`, which gives `veradact_app` its dev login and creates `veradact_test`; local hosts only. A hosted project runs the same Drizzle migrations as its `postgres` role (ARCHITECTURE §17.1). The Supabase CLI is a prerequisite like Docker was, not an npm dependency: the npm package downloads the binary in a postinstall script.
- **Not adopted:** Supabase Auth, supabase-js, Storage, Realtime, Edge Functions, the Data API.
  - Auth stays our own magic link (D-016, D-045): scanner-safe POST consumption, sessions resolved by definer functions.
  - RLS keys on `app.org_id`, set by `withTenant`, not on JWT claims.
  - Client pages may not load third-party scripts.
  - A REST path to the tables would bypass the commands that keep the log and projections consistent (invariants 1, 2, 10).
- **Supabase's API roles are locked out.** A Supabase project gives `anon`, `authenticated` and `service_role` every privilege on whatever its `postgres` role creates in `public`, and the Data API acts as those roles. Verified on the local stack before the fix:
  - with an anon JWT, `POST /rest/v1/rpc/jobs_list_org_ids` listed every org id;
  - `rpc/auth_find_user_by_email` resolved a user;
  - `DELETE /rest/v1/rate_limit_bucket` succeeded, which resets the login rate limits;
  - only RLS kept tenant rows hidden.

  Migration 0006 fixes this:
  - it revokes every privilege those roles hold on tables, sequences and functions in `public`, and on the schema itself;
  - it revokes PUBLIC's USAGE on `public` (only the owner, `veradact_app` and members of `pg_read_all_data` — Supabase's own platform roles — keep it), so objects other roles create there stay unreachable. Supabase installs extensions such as citext as `supabase_admin`, whose default privileges grant the API roles everything and which the migration role cannot change;
  - it removes the default privileges that would grant them again for objects later migrations create;
  - it enables RLS on `rate_limit_bucket` with a single policy for `veradact_app`.

  `supabase-roles.int.test.ts` checks schema usage, every privilege through `has_*_privilege` (so PUBLIC, inherited and column grants count), default privileges, and refusals under `SET ROLE`. `reset-test-db.ts` gives `veradact_test` the grants a real public schema and Supabase give a project's own database, so the test fails if a migration lets the roles back in; with 0006 replaced by a no-op, 8 of its 9 tests fail. Hosted projects should also turn the Data API off.
- **Owner role: `postgres`.** On Supabase it is not a superuser, but it has `BYPASSRLS`, creates roles, and may set `session_replication_role` through supautils, so `pnpm seed --reset` and the tamper tests run unchanged. `veradact_admin` exists only in older migration comments; any owner role works on plain Postgres, and migration 0006 is a no-op there.
- **The dev-only guards check where postgres.js really connects.** postgres.js lets `?host=` in the URL override the host, so `bootstrap-local.ts` and `seed --reset` read its parsed options (`connectionHosts`, `isLocalDatabaseUrl` in `packages/db/src/local.ts`) instead of `new URL(url).hostname`. `seed --reset` also refuses `*.supabase.co`/`*.supabase.com` even with `--force`. A forced purge of any non-local database is refused inside the transaction when supautils is loaded, which catches a hosted project reached by IP or CNAME. On hosted Supabase the `postgres` role may skip triggers, so the old "superuser required" backstop no longer applies. `migrate` uses the same `DATABASE_CA_CERT_FILE` TLS options as the apps.
- **The production runbook (§17.1) closes what an independent security review found:**
  - the app role's password is set with psql `\password`, because Supabase logs DDL and an `ALTER ROLE … PASSWORD` would leave it in plain text;
  - `pnpm db:cloud-setup` does the hosted setup in one command: migrations, a random app-role password sent as a SCRAM verifier so the plain text never reaches Supabase's DDL logs, `DATABASE_URL` written into the gitignored `.env.cloud`, and a login check;
  - TLS to `*.supabase.co`/`*.supabase.com` is always verified against Supabase's public root CA, built into `supabase-ca.ts` (checked against the live pooler certificate; system roots fail with "self-signed certificate in chain"). `DATABASE_CA_CERT_FILE` covers other providers. `NODE_EXTRA_CA_CERTS` is read before Next loads `.env` and would trust that CA for every TLS connection;
  - Supabase Auth sign-ups off, network restrictions on, no extensions that make outbound connections (pg_net, http, dblink, postgres_fdw);
  - an accepted residual risk: the platform's own roles bypass RLS, and server logs and backups hold data outside the erasure model for their retention period.
- **Postgres 17**, Supabase's current major (the CLI offers no 16). The whole suite passes on 17.
- **Pooling needs no code.** `withTenant` sets `app.org_id` transaction-locally, so Supavisor's transaction mode is safe. postgres.js reads `prepare=false` and `sslmode` from the connection URL.
- **Supabase advisor warnings left on purpose:**
  - `citext` lives in `public`, because the definer functions pin `search_path = public, pg_temp`.
  - `app_current_org()` has no pinned `search_path`: a `SET` clause would stop Postgres inlining it into every RLS policy, and its body only calls `pg_catalog` functions.

### D-062 · Self-serve sign-up behind `SIGNUP_ENABLED` (amends D-030)
The owner asked for sign-up: anyone can create an org and become its admin, then invite others (existing invite flow).
- **Flow.** `/signup` takes an email and always answers "check your email" (no enumeration, delivery after the response). A new address gets a 30-minute link to `/signup/complete`; an address that already has an account gets a note pointing to `/login` instead. The link's page asks for the org name and the user's name; submitting creates the org and its admin and opens a session (`auth.signup` + `auth.login` audited).
- **Nothing is stored before the account exists.** The link carries the email sealed with AES-256-GCM under a key derived by HKDF from `LINK_SIGNING_SECRET` (separate from the link HMAC key), so the URL holds no readable address and cannot be forged, and no pending-signup table (PII outside the erasure model) is needed. The token is not single use: it stays valid until the account exists, after which the email is taken and the link answers "already has an account". GET only decrypts and renders the form, so mail scanners that prefetch the link create nothing. `/signup/complete` is excluded from Next's request log and sent with `Referrer-Policy: strict-origin` (the Referer never carries the token; `no-referrer` would make browsers send `Origin: null` on the form POST, which Next 15's server-action handler rejects with a 500).
- **One new definer function**, `signup_create_org(org_id, name, slug, user_id, email, user_name, created_at)` (migration 0007): the app role still cannot INSERT into `org`. It inserts the org and its admin together and returns no row on any unique violation (email taken, slug collision), rolling back both inserts. The app calls it only with an email from an authentic token.
- **AI starts off** for self-serve orgs (invariant 9), so nothing reaches a model provider until an admin turns it on in settings. Operator-created orgs keep the column default.
- **Slugs** are the a-z0-9 words of the org name (accents stripped, ≤ 30 characters) plus 6 random hex characters, matching `org:create`'s slug rule.
- **Off unless `SIGNUP_ENABLED=true`.** Disabled, `/signup` says sign-ups are closed, the login page hides its link, and both core functions return `disabled`. Rate limits: requests 10 / hour per IP and 3 / hour per email; completion 30 / 15 min per IP.
- **Accepted risks (owner's call, shipped as is).** A security review found two gaps that open sign-up creates in features built for operator-created orgs:
  - *AI cost.* A self-serve admin can turn AI on, and there is no per-org quota, so anyone who signs up can run extraction billed to `ANTHROPIC_API_KEY`. Mitigations if this is abused: `SIGNUP_ENABLED=false`, or an operator-only AI permission or a per-org usage cap.
  - *Invite squatting and enumeration.* Emails are unique across orgs (one org per user), so an admin of a self-serve org can invite an address and tie it to their org; the real owner who later signs in lands in that org. The invite conflict message also tells the inviter whether an address is registered elsewhere — the D-060 invite-rate-limit residual risk assumed orgs were operator-created; now anyone can create orgs and probe 20 addresses per hour per org. A full fix needs invitations that take effect only when the invitee accepts, or multi-org membership.

### D-063 · Vendor app visual identity and proof on screen
The vendor app looked like an unbranded admin panel and showed none of what the product proves.
- **Theme in `globals.css`.** One brand colour, `ink` (deep navy, `--color-ink-*`), for primary buttons, focus rings, active navigation and the mark; a warm `paper` page background. Status colours stay semantic and never use ink: green confirmed, **blue pending** (was amber: pending means waiting on the client, not something to fix), red disputed, amber needs review. "AI on" is violet so it reads apart from pending.
- **Newsreader** (serif) for page titles, the engagement name, item statements and headline numbers, loaded with `next/font/google`: the font is downloaded at build (and first dev compile) and served from our origin, so browsers never contact Google. Cost: a build needs network access to Google Fonts. Client pages are route handlers with their own stylesheet and stay on system fonts.
- **Proof made visible.** The ledger opens with a summary (share confirmed, a segmented confirmed/pending/disputed bar, legend entries that link to the filtered ledger) and a "Chain verified" seal from `verifyEngagementChain`, which links to Export. The ledger re-verifies the chain on every view, like the export page; for pilot-sized logs this costs milliseconds (the same assumption as D-006). The seal is only shown for a verification run on that request. The engagements list is a grid of cards with the same bar, one `getEngagementSummary` per engagement — fine for a handful of engagements per org, replace with one grouped query if that grows.
- **Metrics meter.** The 5-day rate is drawn on a 0–100% track with the kill and target marks; the thresholds are `RATE_KILL` / `RATE_TARGET` exported from `domain/metrics.ts`, which `rateBand` uses too.
- **No new dependencies**: icons are inline SVG (`components/icons.tsx`). `KindChip` imports `KIND_LETTER` from core, so it is not re-exported from the `@/components` barrel, which client components import.
- **`ActionForm` layout classes moved to its fieldset.** The fieldset was `display: contents`, so `space-y-*` on the form never spaced the fields (most forms rendered with inputs touching their buttons).

### D-064 · Demo password sign-in for the seeded demo org, development only (amends D-016)
The owner asked for an email-and-password login to the demo account, so a demo does not depend on opening a magic link in Mailpit.
- **One shared password from the environment**, `DEMO_LOGIN_PASSWORD` (8+ characters; empty or shorter = off, the default and the `.env.example` value). No password column, no hashing at rest: it is configuration, compared in constant time (sha256 + `timingSafeEqual`).
- **Never in production.** With `NODE_ENV=production` the feature is off whatever the variable says, and the web server logs `auth.demo_login.ignored_in_production` at startup when it is set. A security review showed why a reachable deployment needs more than a password: any holder is an admin of the demo org and can create non-expiring API tokens, invite their own address (a seat that outlives a password rotation), send invite and confirmation emails from our domain with their own text, turn AI on at our cost, and read whatever other visitors typed. A hosted demo would need a demo-org flag that blocks those (and short demo sessions); not built.
- **Only demo-org users at `.example` addresses.** The user must belong to the org with slug `DEMO_ORG_SLUG` (`quillfield`, which the seed uses; `DEMO_LOGIN_ORG_SLUG` overrides it for a custom `--slug`) and have an address under the reserved `.example` TLD (RFC 2606). Self-serve slugs always end in random hex, so no sign-up can take the slug. Checking the org matters: an `.example` user can exist in any org (a customer admin inviting a placeholder such as `qa@acme.example`), and the address rule alone would hand that tenant to anyone with the password. A wrong password, a non-demo address, a user of another org and an unknown or deactivated user give the same answer.
- **Same session and audit as a magic link**: `openSession` (shared with `verifyMagicLink`, kept internal to `core/auth`) creates the 30-day session and audits `auth.login` with `method: demo_password`. The login page shows a separate "Demo account" form only while the feature is on. Rate limit 10 attempts / 15 min per IP (`demo_login_ip`).
